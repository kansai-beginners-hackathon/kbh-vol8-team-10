# データ出典

このアプリが使う時刻データの**出どころ・取得方法・取得日**をまとめたページです。
調査記録・実測の全文・API 仕様は別ファイルにあります（各節からリンク）。

> **時刻はすべて参考値です。** 実際の乗車前に各交通事業者の公式情報をご確認ください。

## 発表・提出用の要約

```
・京都市営地下鉄：京都市交通局ハイパー地下鉄ダイヤ（www2.city.kyoto.lg.jp/kotsu/tikadia/）を
  スクリプトで取得し、結果の JSON をコミット（31駅）
・叡電・嵐電・阪急京都線・京阪本線+鴨東線・近鉄京都線：各社公式時刻表（HTML/PDF）から
  沿線全駅を人が転記（99駅）。叡電の一部は PDF 解析スクリプトで自動取得
  → 地下鉄と合わせて重複除き 125 駅
・候補地8か所 → ハブ7か所の所要・最終：Yahoo!乗換案内で実測（+3分の安全マージン）
・取得日は全 JSON の source.retrievedAt に記録。ダイヤ改正は事業者ごとに不定期
  （収録: 京阪 2026-08-22 / 近鉄 2026-03-14）
・Transit API（第三者API）：ローカル JSON で解けないハブ→自宅の経路探索にのみ使用。
  候補地→ハブと順位計算はローカルデータと lib/calc.ts
```

## 2. ダイヤ改正について

**改正の時期は事業者ごとに不定期です。**「年1回・春」ではありません。収録時点で公式に確認できた改正日：

| 事業者 | 収録しているダイヤ |
|---|---|
| 京阪 | **2026-08-22 変更**版 |
| 近鉄 | **2026-03-14** 現在のダイヤ |
| 京都市営地下鉄・嵐電・阪急・叡電 | 公式ページにダイヤ改正日の記載なし（各 `source.note` に明記） |

更新するときは、JSON を差し替えたうえで `source.retrievedAt` を取得日に書き換えてください。地下鉄は `npm run data:export` で再取得できます。私鉄 5 社は公式時刻表を見て手で直します。

## 3. 候補地 → ハブの実測（Yahoo!乗換案内）

候補地 8 か所（四条・京都駅・烏丸御池・三条・出町柳・北大路・山科・桂）から、ハブ 7 か所（出町柳・三条・京都河原町・烏丸御池・四条・京都・四条大宮）への**所要時間と最終便**は、Yahoo!乗換案内で人が引いた実測値です。

**検索条件** — 平日 2026/08/31（月）／ 土休日 2026/08/30（日）、23:00 起点、IC 優先、徒歩速度 標準。終電検索（`type=2`）の候補 6 本のうち**出発時刻が一番遅いもの**を採用。

**実在の便の収録** — 終電検索だけでは深夜の 6 本しか取れないため、**出発時刻検索（`type=1`）を 20:00 / 21:00 / 22:00 起点で 3 回**足し、重複を除いて `data/venue-hub-trains.json` に `[発, 着]` で収録しています。これは「逆算した時刻に電車が走っていない」問題を避けるためで、`lib/calc.ts` の `branchLimit` が実在の便から選びます（該当便が無い時間帯・収録の穴は逆算に戻す）。

**安全マージン +3 分** — Yahoo! の表示所要分に **+3 分**して `data/network.ts` の `transitMin` に書いています。実測メモ（`docs/候補地ハブ実測.md`）の表は **+3 前の生の値**なので、突き合わせるときは注意してください。

**注意点**

- 所要分は**最短ルート**の値です。**最終便は遠回りになることがあります**（北大路→出町柳: 最終便 50 分 / 最短 21 分）
- 深夜 0 時台は `24:xx` 表記（`00:xx` に丸めない）
- 平日と土休日で差が出るのは 6 セル・各 1 分だけ
- 2026-08-30 に 8 マスを実ブラウザで再確認し全一致。全 102 マス（51 区間 × 平日/土休日）で「所要分 = 着 − 発」を検算済み

実測の全文は [`docs/候補地ハブ実測.md`](./候補地ハブ実測.md)。

> 出典: Yahoo!乗換案内（LINEヤフー株式会社 / 株式会社ヴァル研究所）。時刻データの権利は各社に帰属します。当該表は本アプリの数値検証のための参照メモです。

## 4. Transit API の位置づけ

`https://api.transit.ls8h.com` は**交通事業者の公式 API ではない第三者 API** です（API キー不要・無料・GET のみ）。仕様と検証結果は [`docs/Transit_API_ガイド.md`](./Transit_API_ガイド.md)。

**使っているのは 2 エンドポイントだけ**（`lib/transit.ts`）:

- `locations/suggest` — 駅名 → 駅 ID
- `plan?type=arrival&time=26:00` — 翌 2:00 までに着く便。**`type=last` は使いません**（ガイド 6-3。このAPIで最大の罠）

**使う場面は「ハブ駅 → 自宅駅」の 1 区間だけ**で、しかも**ローカル JSON で解けなかったときのフォールバック**です（`lib/resolveLastTrain.ts`）:

```
resolveLastTrain(hub, home, dayType)
   ├─ lastTrainBetween(ローカル JSON)   found → via "local"
   ├─ Transit API plan type=arrival     通れば → via "transit"
   └─ 何も無い / 4xx / 5xx / 通信断     → unavailable（UI では「対応予定」）
```

**Transit を使っていないところ**（誤解しやすい点）:

- **候補地 → ハブ**には使っていません（3 章の Yahoo! 実測を静的データ化したもの）
- **順位・最遅出発時刻・最初に詰む人の判定**は `lib/calc.ts` がローカルで計算します（要件定義 §6 の式）

**明らかにおかしい経路は捨てています**（`isSane` / `usesShinkansen` / `startsAt`）: 翌朝 27:00 以降着、20 時前発、区間の間に 60 分超の待ち、新幹線を使う経路、`geo:` 出発が近くの別駅にスナップされた経路。

## 5. 既知の不整合

- `package.json` の `data:import:kyoto-bus` と `data:import:kyoto-bus-timetables` は、指すスクリプト（`scripts/import-kyoto-city-bus.mjs` / `scripts/import-kyoto-city-bus-timetables.mjs`）が**リポジトリに存在しません**。[`data/README.md`](../data/README.md) の京都市バスの手順も同様です。バスは現行の終電計算に使っていないため、実害はありません。
