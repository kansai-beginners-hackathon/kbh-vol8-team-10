## ✗ の原因（2 パターンに分かれた）

### 原因 A: 候補地 → ハブ を「いつ出ても transitMin 分」として扱っている（本質的）

`lib/calc.ts` の式は

```
viaBranch = 支線の最終 − transitMin − transferMin
```

で、**候補地 → ハブ の電車が何時に出るかを見ていません。** 「その時刻に出発できる電車がある」前提になっています。深夜は候補地 → ハブ の本数が 15〜20 分に 1 本まで減るので、**アプリが出す時刻が「電車と電車の間」に落ちる**ことがあります。

**実例: 出町柳 → 桂（アプリ 23:52 / 実測 23:42）**

| | |
|---|---|
| 阪急 京都河原町 → 桂 の最終 | **24:10** 発（`hankyu-last-trains.json` と Yahoo! で一致） |
| アプリの計算 | 24:10 − 15（出町柳→河原町）− 3（乗換）= **23:52** |
| 実際の 京阪 出町柳発 | … 23:42（河原町 23:54 着）／ 23:57（河原町 24:09 着）／ 24:06 |
| 23:57 に乗ると | 河原町 24:09 着 → 24:10 発の阪急に **乗換 1 分** → Yahoo! は不成立と判定 |
| つまり本当の最終 | **23:42 発** |

アプリは「23:52 までに出れば OK」と言いますが、23:52 に出町柳にいる人が乗れるのは 23:57 の電車で、**それでは間に合いません。**

### 原因 B: `data/hubs.ts` の `transferMin` が Yahoo! の想定より短い

**実例: 三条 → 国際会館（アプリ 23:41 / 実測 23:22、差 −19）**

| | |
|---|---|
| 烏丸御池 → 国際会館 の最終 | **23:55** 発（`subway-last-trains.json`） |
| アプリの計算 | 23:55 − 11（三条→烏丸御池）− 3（`transferMin`）= **23:41** |
| 三条(京阪) 発の東西線 | … 23:22（烏丸御池 23:30 着）／ **23:44**（烏丸御池 23:52 着） |
| 23:44 に乗ると | 烏丸御池 23:52 着 → 23:55 発の烏丸線に **乗換 3 分**。Yahoo! はこれを不成立と判定 |
| Yahoo! の答え | 1 本落として **23:22 発**（烏丸御池で 25 分待って 23:55 に乗る） |

`data/hubs.ts` の `transferMin` は 烏丸御池 = 3、四条 = 3、京都河原町 = 3 です。**烏丸御池の東西線 ↔ 烏丸線は階をまたぐ乗換なので 3 分は短すぎる**と思います（Yahoo! は 5 分程度を見ている）。ここを 5 分にすると、この系統の ✗ はかなり減るはずです。

### 参考: 市バスのルート（3 件）

北大路 → 太秦天神川 / 出町柳 → 国際会館 / 四条 → 太秦天神川 の実測は、Yahoo! が **京都市営バス**を使うルートを最終便として返しました。アプリは候補地 → ハブに鉄道しか持っていないので、この 3 件は条件が揃っていません。ただし **バスを使わない鉄道だけのルートで比べても、この 3 件はやはりアプリの方が遅い**（例: 北大路 → 太秦天神川 は鉄道だけだと実測 23:15）ので、原因 A・B と同じ話です。

## その他に気づいたこと

### 1. 【要対応】LP の「例を見る」で 鞍馬 の人が「対応予定」になる（デモに直撃）

`http://localhost:3000/app?m=田中:鞍馬,...`（`app/page.tsx` の `DEMO_HREF`）を開くと、画面に

> この **3 人** が一番長くいられる場所 ／ **（対応予定 1人を除く）**

と出て、**田中さん（鞍馬）が順位計算から外れます。** 4 人のはずが 3 人で計算されます。実際の HTML で確認しました。

原因は `data/prebuilt-stations.json`（`fetchedAt: 2026-08-29`）で、**鞍馬 が `unavailable.weekday` と `unavailable.weekend` の両方に入っている**ことです。`components/Planner.tsx` の `prebuiltFor()` は

```ts
if (hit) stations[m.station] = hit;
else if (PREBUILT.unavailable[dayType].includes(m.station)) unavailable.add(m.station);
else remaining.push(m);      // ← unavailable の駅は remaining に入らない
```

なので、**一度 `unavailable` に焼かれた駅は `buildStations` で解き直されることが無く、永久に「対応予定」のまま**になります。

いま `resolveLastTrain` を直接呼ぶと 鞍馬 はちゃんと解けます（ローカル JSON、出町柳 22:30）。

```
weekday : 出町柳=22:30(local)  三条=×  京都河原町=×  烏丸御池=×  四条=×  京都=×  四条大宮=×
weekend : 出町柳=22:30(local)  （同上）
```

`buildStations(["鞍馬"], "weekend")` も `unavailable: 0` で

```json
{"name":"鞍馬","routes":[{"hub":"demachiyanagi","transferMin":5,"last":"22:30","via":"local","transferCount":0}],"taxiKm":0}
```

を返します。**つまり JSON が古いだけです。**

#### ⚠️ ただし `node scripts/export-prebuilt-stations.ts` をそのまま再実行しないでください

再生成すると 鞍馬 は直りますが、**今度は 大阪梅田 が壊れます。** Transit API が今日は 大阪梅田 への経路を返さなくなっているためです（API 自体は生きていて、宇治などは返ります）。

```
plan geo:京都 → scrape-hankyu:阪急電鉄-京都線-大阪梅田  date=20260830  → {"journeys":[]}  (HTTP 200)
plan geo:京都 → scrape-hankyu:阪急電鉄-京都線-大阪梅田  date=20260831  → {"journeys":[]}  (HTTP 200)
plan geo:三条 → scrape-keihan:京阪電気鉄道-宇治線-宇治   date=20260830  → journeys あり
```

いまの `prebuilt-stations.json` には 大阪梅田 が「昨日取れた値」で残っているので画面では動いています（鈴木さん 23:45）。**再生成 = 昨日の値を捨てる**ことになります。

**安全な直し方は、鞍馬 の 2 行だけ手で足すことです。** `data/prebuilt-stations.json` の `stations.weekday` と `stations.weekend` に

```json
"鞍馬": {"name":"鞍馬","routes":[{"hub":"demachiyanagi","transferMin":5,"last":"22:30","via":"local","transferCount":0}],"taxiKm":0}
```

を足して、`unavailable.weekday` / `unavailable.weekend` から `"鞍馬"` を消す。値はアプリ自身の `buildStations` が返したものそのままです。

（根本対応をするなら、`prebuiltFor()` で `unavailable` の駅も `remaining` に入れて解き直させる、が正しいと思います。「焼いた失敗」が永久に残る構造が本体の問題なので。）**どちらもコード／既定データなのでリクトさん判断でお願いします。こちらでは触っていません。**

### 2. 24 時台の表示が `00:09` になる

`lib/time.ts` の `toStr` が `% 24` するので、解散時刻が 24 時台のとき画面に **`00:09`** と出ます（例: 自宅が桂・候補地が四条）。計算は正しい（内部は 1449 分）ので順位は壊れませんが、**「00:09 までに出れば」は深夜 0 時すぎのことだと分かりにくい**ので、`24:09` 表記にした方がいいかもしれません。

### 3. 検証の再現方法

このファイルの数字は、画面をポチポチ押すのではなく **アプリと同じ関数（`buildStations` → `rankVenues`）を Node から直接呼んで**出しました。`docs/受け入れ検証_再現メモ.md` に手順を残してあります。
